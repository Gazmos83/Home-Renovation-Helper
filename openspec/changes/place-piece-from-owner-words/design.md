## Context

See proposal.md for the reported turn and its trace, taken from the checkpointer for thread `c8d0c885…` ("Sideboard (copy)").

Current code:
- `plugins/ask_placement/tool.py`: `preview` always returns `Questions` (two, or three when hung), and `run` reads the answers by position. A `preview` that returns `None` runs the tool with no pause (`tools/base.py`).
- `foreman.py`: a `views_in_room` decision routes to `"builder" if placement_ready else "designer"`. `after_designer` hands the turn to the Builder when `placement_saved`. The Builder's note tells it to call `render_turntable … in_room true`, which `rooms-only-renders` now refuses.
- `compose_room` requires `items`. `compositions.propose` refuses an unapproved piece version. `compositions._scope_document` already reads a scope's latest (or approved) document.
- Piece approval exists only on the HTTP route (`api/packages.py`), through `house_file.approve_version`.
- `ToolContext.last_message` carries the owner's latest message text, composed by code.
- `conftest.py` already gates `live` and `blender` behind `--live` and `--blender`.

## Goals / Non-Goals

**Goals:** stated placement values are never asked again; a placement turn ends at a room proposal; nothing on this path renders; a benchmark replays the reported sentence on the real models.

**Non-Goals:**
- Changing `room_fit`, the fit maths or the placement file format.
- Changing the approved-only rule for compositions.
- Parsing placement words in code. The model still reads the sentence, and code only checks its numbers.
- A general benchmark harness beyond what this case needs.

## Decisions

1. **The model extracts and code verifies.** `AskPlacementArgs` gains `wall: int | None`, `distance_mm: float | None`, `from_wall: int | None` and `gap_mm: float | None`. A passed number is kept only when it appears as a number token in `ctx.last_message`, compared after normalising the decimal comma. *Alternative:* a regex parser for "wall N … M mm from …". It is brittle with German and English phrasing, and the owner chose "use stated values" with this check.
2. **Partial sets.** `preview` returns `None` when the wall and the distance (and the gap, when hung) are all kept. Otherwise it returns `Questions` with only the missing questions. `run` recomputes which values were missing in the same way, from the same arguments and message, and reads the answers in that order. *Changed during apply:* the planned internal `key` on each question was dropped, so the question payload and the frontend stay unchanged.
3. **`from_wall` conversion in code.** The next wall (`wall % n + 1`) is the left end, so `left = d`. The previous wall is the right end, so `left = length − d − width`. A wall that is not next to the chosen one makes `preview` drop the distance, ask its question, and add a one-line plain note to the question set. The room contract numbers corners counter-clockwise, with wall i running from corner i to corner i + 1, so the end corner of wall i is shared with wall i + 1 and is on the left of someone facing the wall. This matches `offset_from_left`. A `from_wall` equal to the chosen wall is treated as a missing distance.
4. **Room proposal over a Builder hand-off.** `after_designer`'s Builder branch is removed. The Foreman routes every `views_in_room` turn to the Designer. On success, `ask_placement`'s result text tells the Designer to call `compose_room` with `with_saved_place: true` now. The Designer note covers both cases: no place means `ask_placement`, a saved place means `compose_room` with `with_saved_place`. *Alternative:* `ask_placement` builds the composition itself. That would need a second pause from one tool, and the pause machinery allows one gated call per round.
5. **`with_saved_place` is filled by code.** `compose_room` takes `with_saved_place: bool = False`, and `items` becomes optional only alongside it; both together are refused. Code reads the room's latest composition document (latest, not approved, so the owner sees the newest arrangement), drops any item for the bound `package_id`, and adds `{id, type: "piece", package_id, version, placement}` from the stored placement. That covers `wall`, `offset_mm` and `mount_height_mm` when the piece is hung. Validation then goes through `compositions.propose` unchanged. The model never copies an item list on this path.
6. **`approve_version` tool.** It lives in a new plugin folder `plugins/approve_version/` (Designer, not toggleable), with no model arguments. It always targets the bound piece's latest built version, taken from `ToolContext` and never from an argument (CLAUDE.md §8). Its `preview` returns a `Confirmation` with subject `approve_version` and the summary "Approve version N of <name>?". `run` calls `house_file.approve_version` on `yes`. A version already approved is refused without a pause ("already approved"). When `compose_room` refuses for approval on the `with_saved_place` path, its refusal text tells the Designer to call `approve_version`.
6a. **`hung` from the owner's words or the piece** (added during apply; owner's decision 2026-10-19, after the live benchmark caught the real Designer passing `hung: true` for a standing sideboard). A piece whose modules are all marked `mounting: wall` is hung. Otherwise the model's `hung` is kept only when the owner's latest message matches a hang word (hang, hung, wall-mounted, hängen). *Alternatives:* spec only (blocks "hang it" for pieces whose mounting is not set) or wording only (left to the model).
6b. **Proposal text in owner terms** (added 2026-10-19). Only the owner-facing text changes: the summary line (`_where` in `app/compositions.py`) and the table's Placement column read `wall {index + 1}, {left:g} mm from the left end`, where `left = wall length − offset − item width along the wall` (the inverse of `offset_from_left`). The wall comes from the item's room geometry, so an apartment item uses its own room. The stored document, `compose_room`'s 0-based `wall`, and the contract's refusal texts stay as they are: the Designer reads those, and its notes already pair the owner number with the index. *Alternative:* switching `compose_room` to owner numbering. That would be a schema change (ladder step 2) touching every stored composition.
6c. **A hang request routes by code** (added 2026-10-19 after the browser pass). In thread c8d0c885 the owner's "Can you hang it now?" went to Intake with no `views_in_room` flag; Intake has no room tool and repeated the earlier refusal. `engineering_chat.hang_request` (the hang words of 6a, moved there as `HANG`, and no engineering term) now counts as `views_in_room` in the Foreman, and the hang words also count as a placement verb in `placement_request`. On the retest the model flagged the same sentence `asks_help`, whose early return to Intake runs before the view rule, so a hang request is never a help turn, and the model's engineering flag alone does not hold it either. The same pass found `mount_height_mm` stored as `1700.0` refused by the composition contract's whole-number check; a piece's mount height is now any number from 0 to 10000 mm, as `offset_mm` is. *Alternative:* rounding in `with_saved_place`, which would leave a model-passed `1700.0` refused.
7. **No render wording.** The Designer instructions say that a placement or "view in room" turn ends with the room proposal and never mentions renders. The Builder's in-room note is deleted. The Builder instruction "when the owner asks to render or restyle a piece…" stays, because it applies only to an explicit request.
8. **Benchmark marker.** `--benchmark` is added in `backend/conftest.py` next to `--live`, with the marker `benchmark` in `pyproject.toml`. The case uses the real `build_graph` with the routed models and the real budget node. Builds are stubbed as succeeded through the existing fixture helpers (no Blender), and `start_build` is a no-op, so the `compose_room` pause is reached without a headless job. The case resumes no confirmation, so nothing is created or built. Assertions read the interrupt payload, the stored placement file and the tool calls in the checkpoint. *Alternative:* reuse `live`. That marker means the gateway probe, and the owner asked for a named benchmark.

## Risks / Trade-offs

- A model may pass `wall` and `distance_mm` while omitting `from_wall` for "from wall 3". The distance would then be read as from the left end, which is correct here by coincidence and wrong for the right end. Mitigation: the tool description and the Designer instruction spell out `from_wall`, and the live benchmark adds a right-end sentence as a second step once the first passes. TODO(user): whether the right-end case belongs in the first benchmark set.
- Number matching is loose: "2" appears in many messages. It guards against invented values, not against the model choosing the wrong stated number. The fit refusal and the room proposal summary are the owner's check.
- The benchmark spends money and depends on the alias `~deepseek/deepseek-v4-flash-latest`, so results can shift without a code change. That shift is the point of the benchmark, and the failure message names the step.
- Removing the Builder hand-off changes `view-piece-in-room` behaviour that has not been archived yet. This change must apply after that change and `rooms-only-renders` are archived, so the MODIFIED requirement exists in the main spec.
