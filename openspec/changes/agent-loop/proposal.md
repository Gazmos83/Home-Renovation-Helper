## Why

After `render-guard` the owner can build and render a package, but only by writing spec JSON by hand and driving routes with `curl`. The product's loop — "describe a change to the bot, confirm, see a new turntable in about half a minute" — needs the conversation: a Foreman the homeowner talks to, an Intake that turns a wish into confirmed numbers, a Designer that emits and revises spec JSON, and a Builder that runs the headless path behind the guard. Every one of them reads the house first, so the house file (the long-term memory CLAUDE.md §9a describes) lands in the same change: Intake writes rooms and style into it, the Designer records pieces and versions, and a change the schema cannot express becomes a recorded generator-extension request instead of a guess. Steps 3 and 4 of §11 together; step 4a (blueprints and photos, the apartment shell) is not included.

## What Changes

- **House file** (step 3): the owner's long-term memory in four tables and a conversation index — `rooms` (measured polygon, height, wall thickness, openings), `preferences` (style and defaults as key/value), `pieces` (one per package id, with its confirmed brief and room) and `piece_versions` (one per `docs/renders/<id>/v<N>`, with what changed and what it was revised from), `generator_extension_requests` (the ladder's step-2 record), and `threads` (the conversations the owner started). Migration `0002`. The checkpointer from the foundation is the short-term memory: one thread per conversation, and a chat turn is refused with a stated reason when the checkpointer is unavailable.
- **Foreman and three specialists** (step 4): one compiled supervisor graph. The Foreman routes each turn to Intake, Designer or Builder with a structured decision from its own model, bounded by what exists (no piece → never the Builder); each specialist is a sub-graph with its own instruction file, its own tools and its own model slot from `config/models.yaml`. The homeowner talks only to the Foreman and never sees a model name, a prompt, a token count or a cost.
- **Intake** collects the brief and proposes confirmed numbers (room, heights and openings, style, budget); on the owner's "yes" they are written to the house file.
- **Designer** emits spec JSON. `create_piece` validates it against the schema, previews it (overall size, modules, cut-list rows, hardware), waits for "yes", then records the piece and version 1 and starts its build. `revise_package` applies a bounded set of stated changes to the stored spec, previews the change lines, waits for "yes", then records the next version and builds it; the earlier version is untouched. `cut_list` returns the derived parts and hardware of a version with no GPU work. `room_fit` checks a placement of a piece against a house-file room — the wall, the offset, the ceiling, the openings and the furnishings — and refuses naming the wall and the excess, or returns the placement a room render uses.
- **Ladder step 2 by construction**: a document naming a field the schema does not define is refused by field name, never built, and the Designer records a `generator_extension_request` (the field, the owner's words, the piece) so the schema and generator can grow through an OpenSpec change.
- **Builder** runs the headless path and nothing else: `blender_build` builds a version and reports its Workbench screenshot; `render_turntable` renders a still or a turntable of a version — alone or placed in a room from `room_fit` — through the render guard with a required tier; a `final` pauses the conversation with the estimate and runs only on "yes". No `bpy` is written by any agent.
- **Chat routes** (owner-gated): start and list threads, send a turn, answer a pending confirmation (`yes`/`no` with an optional reason), read a thread. Every turn carries the owner, thread and piece into Langfuse and records usage per call under the slot's model.
- **Carried over from the predecessor**: the tool-loop graph shape with `interrupt()` before a gated tool runs, the instruction-file format (YAML header naming tools; only the text is editable later), prompt assembly with the untrusted-content guard composed by code after any editable text, neutralising of owner-authored strings in context notes, the bounded tool-round cap, and the scripted `FakeChatModel` for tests.
- **Dropped**: stages selected from quotes and pricing, projects and clients, messages to a client, remnants, material review, plugins and feedback policy (steps 5, 7 and 9), and the token budget (`budget.py`, step 7 — this change trims history by message count in code).

**Ladder step and agent:** ladder step 1 (spec change → headless build and render) for the Designer and Builder, and the step-2 record (generator-extension request) when the spec cannot express a change. Agents bound: Foreman, Intake, Designer, Builder. **Render guard:** used, not changed — the Builder's renders pass through `authorise`/`run_render` with a required tier and the graph-side `interrupt()` for `final`. **bpy allow-list:** not affected; no live socket.

## Capabilities

### New Capabilities
- `house-file`: the owner's long-term memory — rooms, preferences, pieces and versions, generator-extension requests, thread index — written by confirmed agent actions and read at the start of every turn.
- `homeowner-chat`: threads, turns, pending confirmations and their resumption over owner-gated routes; what the homeowner may see; refusal when memory is unavailable; tracing and usage per turn.
- `design-agents`: the Foreman's routing, the Intake/Designer/Builder behaviours, the confirmation each gated tool needs, the refusal-by-field-name path, and the Builder's use of the render guard.

### Modified Capabilities
None. `furniture-packages` and `scene-rendering` are consumed as they stand (the Designer and Builder create versions and renders through the same code the routes use); `render-guard`'s "Final inside a graph" scenario is implemented here, not changed.
