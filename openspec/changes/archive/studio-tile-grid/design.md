## Context

`routes/Studio.tsx` renders the shared left rail (`components/chat/Rail.tsx`) and one `Page` holding the chosen tab's body. `App.tsx` routes `/studio` and `/studio/:tab` only. `Pieces.tsx` (one `Piece` card per piece), `Rooms.tsx` (`MeasuredRoom` and `CompositionCard`) and `ModelLibrary.tsx` (one card per model and an inline upload form) each render full cards in a single column. `Page` caps content at `max-w-5xl` unless `wide`. `components/ui/` has no dialog. Only `@radix-ui/react-label` and `react-slot` are installed. three.js, `@react-three/fiber` and `drei` are installed (`PieceModel.tsx` loads GLBs with `useGLTF`).

On the backend, `ModelOut` returns `files` (every stored file but `check.json`) and no entry name. The model's `entry` is a DB column. Files are served by `GET /models/{id}/files/{name}` from `<upload_root>/models/<id>/`, with content types from `CONTENT_TYPES` (png included). There is no picture of a model.

Owner decisions (2026-10-14): sub-menu column, top tabs on a phone; browser snapshot for model pictures; the same grid for all three tabs; pages of 16 or 6, not scroll; tile style A (image card with caption); shadcn Dialog; addressable dialogs (chosen after asking which option has the least latency: both are client-side and the difference is not noticeable, so the choice is about behaviour).

## Goals / Non-Goals

**Goals:** the grid, sub-menu and dialog shell from the specs; the existing card bodies moved into dialogs with no change to their logic, queries, refusals or tests' assertions about content; the model preview picture end to end.

**Non-Goals:** no redesign of what a piece, room or model shows; no new filters, sorting or search; no change to Pricing Overview, AI & Agent Settings or the conversation page; no Blender work; no change to the inspector route.

## Decisions

- **Routes: one splat route, the dialog read from the path.** `App.tsx` adds `/studio/:tab/*`. `Studio` reads `tab` and the rest of the path (`<id>`, `upload`, `compositions/<slug>`) and passes the item key to the tab body. The grid stays mounted while a dialog opens or closes, so closing does not rebuild or refetch it. Opening is `navigate(<item path> + location.search)`, which pushes a history entry so Back closes the dialog. Closing (Esc, close button, outside click) is `navigate(-1)` when the dialog was opened from the grid in this session (tracked in `location.state`), and otherwise `navigate(<tab path> + search, { replace: true })`, so a dialog reached by a link never sends Back out of the app. *Alternative:* nested `<Route>` elements per tab. More files for the same result.
- **Room addresses use the name, encoded.** `/studio/rooms/<encodeURIComponent(name)>`, matching how pieces are addressed by id. Standalone compositions live under `compositions/<slug>`, which is two path segments, so a room named "compositions" still resolves (its encoded name is one segment). Models use their UUID, and `upload` cannot collide with one.
- **Shared pieces, kept small.** `components/ui/dialog.tsx` is the stock shadcn Dialog over `@radix-ui/react-dialog` (focus trap, Esc, return focus, `aria-labelledby` come from Radix). The content class is full-screen below `sm` (`inset-0 h-dvh w-screen rounded-none`) and centred at `sm:` (`sm:max-w-3xl sm:max-h-[90dvh] overflow-y-auto`). `components/studio/` gets `Tile.tsx`, `TileGrid.tsx` (paging and the `?page` sync) and `SubMenu.tsx`. All three tabs use them, which is the abstraction the owner asked for ("same grid for all three"). *Alternative:* the native `<dialog>`. Rejected by the owner.
- **Tile (style A) in Tailwind.** `button` → `flex h-full flex-col overflow-hidden rounded-lg border bg-card text-left shadow-sm hover:ring-2 hover:ring-primary focus-visible:ring-2 focus-visible:ring-ring`. The picture area is `relative min-h-0 flex-1 bg-muted` with `img.size-full object-contain p-2`, and the badge is `absolute right-1 top-1`. The caption is `p-2` with name `truncate text-sm font-medium` and detail `truncate text-xs text-muted-foreground`. The placeholder is the tab's lucide icon (Armchair / Ruler / Package) at 32 px in `text-muted-foreground`. The image area flexes rather than using `aspect-square`, because a square image plus caption at 4 × 4 is about 1100 px tall on a 1280 × 800 laptop. Flexing is what lets four rows fit.
- **Filling the screen.** The grid is `grid grid-cols-2 grid-rows-3 lg:grid-cols-4 lg:grid-rows-4 gap-3` with `min-h-[24rem] lg:min-h-[32rem]` (8 rem a row, so a short screen scrolls rather than squashes; 9 rem made Pieces scroll at 1280 × 800 and 360 × 780 in the browser pass). Its height is set inline to `calc(100dvh - <its own top on the page + room for the pager and bottom padding>px)`, measured on mount and on resize. Each tab has a different intro above its grid (Pieces has a button and two lines), so the grid measuring itself is simpler and exact, compared with Studio keeping a shared offset variable. Rows are `minmax(0, 1fr)`, so a short last page keeps the same row heights. The Studio content uses `Page wide`, because at `max-w-5xl` beside two columns the tiles are about 200 px wide. `dvh` keeps the phone grid clear of the browser bar on the S25.
- **Page size follows the breakpoint, not the item count.** `useMediaQuery("(min-width: 1024px)")` (a ~10-line hook over `matchMedia`, in `lib/`) gives 16 or 6. Crossing it recomputes the page as `floor(firstShownIndex / newSize) + 1` and replaces `?page`. Out-of-range `?page` values clamp, as the spec requires. jsdom has no `matchMedia`, so tests stub it in `test/setup`.
- **Sub-menu.** `SubMenu` is a `nav` of `NavLink`s. At `md:` it is a `w-44 shrink-0 border-r` column. Below `md:` it is an `overflow-x-auto flex gap-2 border-b` row rendered inside the content above the grid. The same component is used, with the layout switched by classes, not by JavaScript. Its links carry the current `?page` where it applies.
- **Card bodies move, unchanged.** `Piece` (the card) becomes `PieceDetail`, rendered in the dialog. Its `section`/`cardClass` wrapper becomes the dialog body and its `h2` becomes the `DialogTitle`. `MeasuredRoom` and `CompositionCard` are treated the same way. Rooms' existing inline delete confirm stays as it is inside the dialog. On a successful delete it closes the dialog by navigating to the grid. The tile data each tab needs is already in its list query: pieces need `pictureVersion` over the per-version queries the card already makes, rooms use `RoomSummary` plus `composition.picture`, and models use `ModelAsset`.
- **Prefetch on hover/focus.** The tile's `onPointerEnter`/`onFocus` calls `queryClient.prefetchQuery` for the queries the dialog mounts first: a piece's `["version", id, n]` and `["renders", id, latest]`; a room's compositions are already loaded. Models need nothing. Same query keys, so no cache is duplicated.
- **Model preview picture, in the browser.** `lib/modelThumbnail.ts` renders off-screen with a plain `THREE.WebGLRenderer({ preserveDrawingBuffer: true })` at 384 × 384 on a light neutral background with one hemisphere and one directional light. The camera is placed on the bounding sphere at a 35° azimuth and 25° elevation, and the scene is fitted. Loaders come from `three/examples/jsm`: `GLTFLoader` for `glb`/`gltf`, and `OBJLoader` + `MTLLoader` for `obj`, with URLs built from the model-file route and the new `entry` field. The output is `canvas.toBlob("image/png")`, then `PUT /models/{id}/thumbnail`. Everything is disposed afterwards. The Uploaded models view runs this for each `ready` model without a picture, one at a time, after the grid has painted. A failure is remembered in memory for the view's lifetime only. `@react-three/fiber` is not used: a one-shot off-screen frame needs no React tree. *Alternatives:* a headless Blender still (needs a guard ticket and the Blender slot per upload) or an owner-supplied photo. The owner chose this one.
- **Backend route.** `PUT /models/{id}/thumbnail` reads the raw body with a hard cap (256 KB + 1, then 413), checks the PNG signature and the IHDR width and height (≤ 512) from the bytes with no image library, and requires `state == "ready"` (409). It writes atomically (temp file + `os.replace`) to `<upload_root>/model-thumbnails/<id>.png`, a sibling of `models/`, so it never shows in `files`, the file route cannot reach it, and an upload cannot overwrite it. `GET /models/{id}/thumbnail` returns `FileResponse(media_type="image/png")` with `nosniff`, or 404. `ModelOut` gains `entry: str` and `has_thumbnail: bool`. `library.delete_model` also unlinks the picture. No migration: the file's existence is the state.
- **Vite proxy.** `/models/...` is already proxied, with the `page` bypass for HTML requests, so `/models/{id}/thumbnail` needs no entry. `/studio/...` is SPA-only.

## Risks / Trade-offs

- [Big Rooms dialog: the 3D view inside a dialog] → The `RoomView` canvas sizes to its container. Inside a scrolling dialog it gets a fixed height (`h-[60dvh]`) so OrbitControls do not fight the scroll. This is checked in the browser pass.
- [A WebGL context per snapshot] → one model at a time, renderer disposed and `forceContextLoss()` after each, so the browser's context limit is never reached even with many models.
- [Snapshot of a model with missing textures] → `ready` already guarantees Blender imported it. If a texture fails in three.js, the snapshot is still taken untextured rather than refused, which is better than a placeholder.
- [Existing tests assert card markup (`section` with `aria-label`, `h2`)] → the card content tests are kept and pointed at the dialog body. Tests open the dialog via its address (`/studio/pieces/<id>`) so content assertions stay the same. The new grid, paging and dialog tests are added alongside.
- [Viewport-filling grid on very tall or very wide screens] → tiles grow, but the image is `object-contain`, so nothing distorts. This is acceptable for a single-user laptop and phone app.
- [`?page` and dialog paths shared in history] → paging uses `replace` (it is not a navigation step), and only opening a dialog pushes, so Back behaves as the spec says.

## Migration Plan

Frontend and one additive backend route. There is no data migration. Models uploaded before this change get their picture the first time Uploaded models is opened. Rollback: revert the commit. Stored pictures under `model-thumbnails/` are then simply unused.

## Open Questions

- Should a tablet width (640–1023 px) get 3 columns? The specs follow the owner's two reference screens (2 × 3 below 1024 px). Changing it later only touches the breakpoint classes and the page-size hook.
- The Pieces and Measured Rooms sub-menus have one view each ("All pieces", "All rooms") for now. Further views (e.g. "Approved only") can be added to the sub-menu later without changing this design.
